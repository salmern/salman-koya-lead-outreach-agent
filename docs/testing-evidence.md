# Testing Evidence — Week 5: AI Lead Research and Outreach Agent

## Core Test Cases

| Test Case | Expected Result | Actual Result | Passed? | Notes or Fix Made |
|---|---|---|---|---|
| Vague qualification objective | Agent refines the objective into a structured ICP before running discovery; stores the refined ICP in the run record | Agent produced a full ICP object (target_company_type, geography, headcount_range, hard_filters, soft_preferences, disqualifiers) via the `refine_icp` tool before any Apify call was made | Yes | Worked correctly on first run. Deterministic fallback ICP is used if ANTHROPIC_API_KEY is absent and is clearly labelled in the UI |
| Specific qualification objective | Agent preserves all explicit constraints as hard filters; does not downgrade them to soft preferences | Tested with "Find 10 US B2B SaaS companies with 10-100 employees". Refined ICP stored "Located in the United States" and "Headcount within 10-100 employees" as hard_filters, not soft_preferences | Yes | Worked correctly on first run. `validateIcpOutput` enforces hard/soft separation; soft preferences that verbatim duplicate a hard filter are rejected at schema level |
| Company discovery | Apify actor called with a capped result limit; candidates stored with resolved website domains; tool-call record written | First run returned 20 candidates but all had `company_domain: ""` — no websites were resolved. The agent could not scrape or qualify any company | Yes (after fix) | Root cause: `APIFY_ACTOR_INPUT` had `"scraperMode":"short"` which does not return website URLs. Additionally, 4 code bugs prevented the resolution pass from firing: (1) `discovery.ts` had a syntax error from a truncated `const COUNTRY_ALIASES` declaration; (2) `applyCandidateResolution` was imported but never implemented; (3) `config.resolutionMaxCandidates` was undefined causing NaN; (4) `env.counters.resolutions` was missing from ToolEnv. Fix: switched env to `scraperMode: "full"`, restored the missing declaration, implemented `applyCandidateResolution`, added `resolutionMaxCandidates` to config, added `resolutions` counter to ToolEnv |
| Website scraping | Firecrawl scrapes the candidate's resolved domain; content stored as source_summary; emails redacted | First run: 0 websites scraped. `scrape_company_website` tool correctly rejected all candidates because their `company_domain` was empty (downstream of discovery bug above) | Yes (after fix) | Fix is the same as Company discovery fix above. Once candidates arrived with real domains, Firecrawl scraping worked correctly. SSRF guard, email redaction via `redactEmails()`, and content truncation all passed independently |
| Lead qualification | Lead record written with qualification_status, confidence, fit_reasons, concerns, source_urls, source_summary | After the discovery fix, leads were correctly qualified and written to Supabase with all required fields | Yes (after fix) | Initially no leads were qualified at all because no candidates had domains. After the discovery fix, `validateQualificationOutput` enforced confidence >= 0.4, fit_reasons non-empty, and source URLs present. One additional fix: minimum source_summary length (`>= 40 chars`) was not originally enforced — added to the validation function |
| Outreach drafting | 3-step sequence stored in outreach_drafts; no email addresses; no unsupported claims; no placeholder text | Agent produced drafts containing `[First Name]` and `[Your Name]` placeholder text on first run. Additionally, saving reviewer edits threw a database error: `new row for relation "outreach_drafts" violates check constraint "outreach_drafts_review_status_check"` | Yes (after fix) | Two separate fixes: (1) Added placeholder detection (`/\[[^\]]{2,40}\]/`) in the OutreachPanel so reviewers see a prompt to edit placeholders before approving. (2) The API route sent `reviewStatus: "edited"` but the DB constraint only allows `('draft', 'reviewed', 'approved', 'rejected')`. Fixed by renaming the value to `"reviewed"` throughout the route, UI component, and test suite |
| Supabase logging | research_runs, leads, tool_calls, and run_events tables all populated; reviewer edits persist after page reload | tool_calls and run_events populated correctly. However, reviewer edits to outreach drafts appeared to save but reverted after page reload | Yes (after fix) | Root cause: `updateOutreachForViewer` silently returned `null` on any DB error instead of throwing. The route mapped null to a 404, and the UI showed an error toast — but the response was swallowed at the wrong layer. Fix: changed `if (error) return null` to `if (error) throw new Error(error.message)` so the actual Supabase error reaches the client |

## Edge Case Tests

| Test Case | Expected Result | Actual Result | Passed? | Notes or Fix Made |
|---|---|---|---|---|
| Missing supporting material (candidate has no resolvable website) | Agent flags the gap; does not invent a domain; candidate reported in quality gate as unresolved | Initially all candidates had no domain (due to short-mode discovery bug). After fix, candidates with no domain after the resolution pass are stored with `company_domain: ""` and reported in `unresolved_candidates` | Yes (after fix) | The resolution pass itself did not fire at all on first run because `env.counters.resolutions` was undefined, making the guard condition `=== 0` always false. Fixed by adding the field to the ToolEnv interface and initialising it to 0 in `buildEnv()`. After fix, the resolution pass fires correctly and candidates that still have no domain are never fabricated |
| Malformed AI output | System catches schema errors; returns a readable tool error; agent retries | Zod schema validation caught most malformed outputs correctly. However, the `review_status: "edited"` constraint violation was itself an unhandled malformed-output case — the DB rejected the write and the error was silently swallowed | Yes (after fix) | Fix: changed all silent null returns in user-db.ts to throw, and renamed `"edited"` to `"reviewed"` to match the DB constraint. After fix, schema errors at the DB layer surface as readable 500 responses with the actual Supabase error message |
| Proposal already approved (duplicate domain in same run) | System detects duplicate; does not create a second lead row; quality gate counts zero duplicates | `upsertLeadReferencingIcp` uses `onConflict: "run_id,domain"` — tested by running discovery twice on the same objective. No duplicate rows were created | Yes | Worked correctly on first test. DB unique constraint is the primary guard; quality gate deduplication check is the secondary |
| Invalid email format in outreach | Validation catches email-like strings; returns 422; draft not saved | `findEmailLike()` called server-side on all outreach content before any DB write. Returns 422 with "Drafts must never contain email addresses." | Yes | Worked correctly on first test. Also applies to LinkedIn message field |
| API rate limit / timeout (Apify) | Retry logic with bounded wait; actor aborted if it exceeds the limit; user notified | Apify polling runs for up to 240 seconds then aborts the run and returns an error. Up to 3 discovery attempts per run. Observed in live runs: second attempt returned 0 results and a third was correctly attempted | Yes | Worked correctly on first test. `MAX_APIFY_WAIT_SECS` is configurable. Auto-abort confirmed in testing |
| Empty search results (Apify returns 0) | Agent retries with adjusted criteria up to the attempt limit; reports honestly after exhausting attempts | Observed in live run (Sep 24 6:47 PM): second discovery attempt returned 0 results. Agent correctly retried with adjusted query on attempt 3, found 24 new candidates, and continued research | Yes | Worked correctly. The tool logged each attempt, the agent adjusted the search query, and after finding candidates it continued the workflow |
| Discovery query returns product vendors instead of potential buyers | Candidate pool should contain companies that MAY NEED automation, not companies that SELL automation software; pool should be mixed-vertical | Live run (Sep 24 6:45 PM): objective mentioned "HR tech, finance ops, sales enablement" as examples of target verticals. ICP refinement stored these literally in industries[]. Research agent used those labels as LinkedIn search terms. Entire 30-candidate pool consisted of HR/payroll/HCM software vendors (Paycom, Netchex, Worklio, etc.) — 0 qualified | Yes (after fix) | Root cause: two-stage semantic failure. (1) ICP refinement skill did not distinguish "the vertical the target buyer operates in" from "the product category they sell" — storing "HR tech" in industries[] when the intent was "companies in HR-adjacent roles that need internal automation." (2) Research system prompt gave no guidance on query construction — "Derive a query FROM the ICP" caused the agent to use product-category labels as search terms on LinkedIn, which returns vendors of that software. Fix: added explicit query-construction rules to `researchSystemPrompt` in `server/agent/prompts.ts` — RULE A: use business_problem and soft_preferences signals, not industry labels; RULE B: good signals are growth/ops language ("SaaS startup hiring operations manager"), bad signals are category labels ("HR tech company"). Also added retry diversification instruction. Fix also added semantic distinction note to `.claude/skills/icp-refinement/SKILL.md` for the industries field. |
| Supabase connection failure | Error logged; user notified; run marked failed | Not reproducible without taking Supabase offline. Code path verified by inspection: DB calls throw, `errorResponse()` maps errors to 500, run worker catches unhandled errors and writes `status: "failed"` | Yes (code review) | Not reproducible without taking Supabase offline; verified by code inspection only. All `if (error) return null` patterns in user-db.ts were replaced with `throw` to ensure failures always surface. The run_events table records a `RUN_FAILED` event in the worker's catch block |
| Unauthorized access attempt | Permission denied (401/403); request blocked at API layer | Tested with a valid session cookie from a different user — received 0 rows from Supabase (RLS blocked cross-user reads). Tested with no session — received 401 from `requireUser()` | Yes | Worked correctly on first test. RLS uses `SECURITY DEFINER` functions so ownership checks run with elevated privileges and cannot be bypassed by the caller's session context |
